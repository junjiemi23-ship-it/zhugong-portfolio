# 运维经验：每天真实运行踩出来的坑

下面每一条都是拿真金白银的故障换来的，不是从文档里抄的。
具体参数按你自己的通道调整，原则通用。

## 1. 重启纪律：绝不能在通道里杀 server 自己

最贵的一次教训：通过通道本身下发"重启 server"的命令。客户端 hang 住，
永远等不到返回，整条通道假死——唯一的恢复方式是人走到电脑前。

正确姿势是**延迟 detached 重启**：独立脚本 sleep 几秒→杀旧进程→再等几秒→
拉起新进程。杀服务的人，不能是服务自己。

## 2. 阻塞红线

绝不在通道里跑可能永久阻塞的命令：无超时的流读取、无硬超时的进程等待，
一律不行。一次卡住，整条通道陪葬，恢复只能靠人去现场。
硬超时必须写在**脚本侧**，不能靠"我觉得这次不会卡"。

## 3. 超时：劣化不等于死亡

网络劣化时，一个简单的"列出任务"调用能慢到几分钟才返回。教训：

- 健康探针的超时至少给 200 秒（我的配置），再判通道死亡。25 秒就放弃
  的不是诊断，是误诊。
- 宣布死亡之前，先看独立巡检的状态（单独的定时巡检是 ground truth）。
  巡检成功而你的手动探针失败，说明是你这次调用或环境的问题，不是通道真死了。

## 4. 环境变量继承坑

Windows 的 `setx` 只写注册表，不影响已运行进程——而旧 server 拉起的新进程
会继承旧环境。后果：

- 改完 runner 白名单必须重启 server，否则它继续执行旧白名单。
- 启动脚本每次从注册表重读配置，重启不再怕环境过期。
- 重启后等 8~10 秒再验证：太早的探针会打到还没死透的旧进程（旧白名单）。

## 5. 白名单工作流

- 白名单是数据不是代码：JSON 映射，runner 名 → 可执行文件 + 固定参数。
- 每次任务的指令是作为**单个参数**追加在白名单 argv 后面的，塞不进 CLI
  flag（会破坏参数解析）。固定 flag 去白名单条目或 runner 自己的配置文件，
  绝不放在每次任务的文本里。
- 改完白名单，每个 runner 用**最小任务逐个验证**再信任。最阴险的是静默零
  执行失败（exit 0，实际啥都没跑）——白名单看着明明是对的。
- 在白名单里把模型 pin 死到免费档。runner 的默认模型可能变、可能撞额度墙，
  显式 pin 住成本才可预测。

## 6. 验收运维

- 任务日志 ~30 分钟无增长，告警**一次**，然后人工决定：等、杀、重派。
  每轮都告警是噪音，告警一次是信号。
- 第二个模型只打分，最终结论 dispatcher 下；不通过就打回重做——
  "它说做完了"永远不算证据，对"但这次看着像做完了"也没有例外。
- 高风险验收让打分模型跑两遍（比如中英各一遍），对照后再下结论。

## 7. Token 与审计，从第一天做起

- 通道 token 只走环境变量或 `0600` 文件，永不进代码、聊天记录、截图。
  一旦进去就按泄露处理、立即轮换——没有"我很小心所以没事"。
- 本地记 append-only 审计日志，每次调用（含被拒绝的）都记一行。
  凌晨两点出问题时，日志是"能 debug"和"只能猜"的区别。
