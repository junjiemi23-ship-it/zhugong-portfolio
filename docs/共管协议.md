# 主公的粮仓 · 双 AI 共管使用协议 v1.1

> 定稿：2026-08-18 · Codex 定稿，主公 2026-08-18 确认生效 · 修订记录见文末
> 用途：Codex（主公主力 AI，出方案/指导/审结果）+ WorkBuddy（执行 AI）+ 主公（唯一决策人）共同管理公开作品集仓库。

## 0. 适用范围与角色
- 仓库：`github.com/junjiemi23-ship-it/zhugong-portfolio`（公开，作品集/求职展示；中文名号「主公的粮仓」）
- 共管方：Codex、WorkBuddy、主公（唯一决策人）
- 规则优先级：主公最新指示 > 本协议 > 双方习惯；修订需主公确认、Codex 定稿。

## 1. 目录结构约定（v1.1 起与 README 门面对齐）
- 根目录：README.md（门面/导航，改动前在 AI交流 声明）
- docs/：文档（含本协议副本 `共管协议.md`）
- 项目目录采用 README 规划的五类顶层目录（不设 codex/、workbuddy/ 等内部目录，AI 间协作走 D:\AI交流）：
  - holiday-pages/ 节假日特定网页
  - surveys/ 调研问卷与数据处理
  - ai-chat/ AI 对话平台实验
  - web-research/ 网络资源与大数据查找
  - chat-companion/ AI 聊天搭子（仅脱敏示例）
- 命名：目录/文件用小写字母、数字、连字符；中文文件名避免空格和特殊符号。

## 2. 提交信息规范
- 格式：`[Codex|WorkBuddy] <类型>: <简述>`；类型=feat/fix/docs/chore/data。
- 必填：来源标签+类型+一句话改动；涉及文件在正文列出。
- 分支：日常小改动直接 main；大面积重构/批量改动先建 `feat/<主题>` 分支，合并前在 AI交流 声明。
- 禁止：空信息、无标签、含敏感信息的提交。

## 3. 并发 / 冲突避免与解决
- 「先声明」= 在 AI交流 写明目标文件+改动内容+预计完成时间，之后才动手；先声明者优先。
- 仓库级管理操作（改名、改描述、改可见性、删分支、转移等）也属写操作，一律先声明；红线三类之外的此类操作不需主公逐次「同意」，但完成后必须汇报。
- 不同目录可并行；同一文件两 AI 不得在 15 分钟内同时改。
- 冲突：先 `git pull --rebase`（沙箱内走 API 时校验 fast-forward）；仍冲突则停手，把冲突文件+双方意图贴 AI交流，由 Codex 仲裁、WorkBuddy 执行；原则=主公意图优先、改动小者让步、可并存则分目录合并。
- 发现对方未声明改动：保留对方版本，通知对方，不擅自覆盖。

## 4. 凭据管理与能力现状
- Codex 侧（目标）：优先 GitHub 插件 Connect（官方授权，权限由授权页控制），或 classic PAT（repo，90 天）配 `GITHUB_TOKEN`。
- Codex 侧（现状，2026-08-18）：插件工具未注入、无 PAT，暂不具备 GitHub 写操作通道；写操作默认由 WorkBuddy 执行，Codex 出方案/审核；通道恢复后更新本条。
- WorkBuddy 侧：`GITHUB_PERSONAL_ACCESS_TOKEN`（已配）。
- token 只存各自安全配置；绝不写进 AI交流/聊天/截图/仓库文件。
- 轮换：到期前 7 天由该侧提醒主公续期；新 token 生效后立即撤销旧 token。
- 泄漏：立即 GitHub 撤销 → 重新生成 → 通知对方 → 检查仓库/文件有无泄露记录并清理。
- 沙箱限制：WorkBuddy 沙箱内本地 git 不可靠，GitHub 推送默认走 WorkBuddy 的 `github-sandbox-api-push` skill（Git Data REST API + fast-forward），不重复尝试本地 git。

## 5. 危险操作确认机制
- 红线三类：删仓库 / force push / 公开敏感信息。
- 流程：AI交流 建「危险操作确认」条目（对象/原因/影响/撤销方法）→ 主公明确回复「同意」→ 才执行；未回复=禁止。
- force push：main 上默认禁止；确需时只允许 `--force-with-lease` 且走确认。
- 提交前检查敏感内容（密钥/手机号/姓名/聊天原文/问卷原始数据）。

## 6. 防差错清单（提交前逐项过）
- [ ] 已 pull --rebase（防分叉；沙箱内改走 API 时校验 fast-forward）
- [ ] 无敏感信息（git diff 复查）
- [ ] 不删/重建同名仓；不覆盖未声明文件
- [ ] 不 force push main；不用 git reset --hard 处理他人分支
- [ ] 提交信息带来源标签
- [ ] 新文件在正确目录（五类项目目录或 docs/）

## 7. 会话交接与上下文管理（v1.1 新增）
- 上下文用量以面板数字为准；无精确数据时不下「快满了/不够用」的结论，把不确定如实摆出由主公拍板。
- 已用 ≥50%：执行方先把关键状态落盘到 D:\AI交流（当前任务/已完成/待办/关键文件路径）。
- 已用 ≥70% 或任务接近上限：必须先写交接文件再换窗口；新窗口首轮读取交接文件。
- 交接文件命名：YYYYMMDD-HHMM-发送方-主题.md，前缀 待处理-/处理中-/已解决-。
- 切换模型不删除记忆文件；对话历史不跨会话；关键规则以文件为准，不依赖模型记忆（记忆只是回顾层）。

## 8. 新项目立项流程（v1.1 新增）
- 项目启动：AI 出一页式方案（目标/范围/技术栈/交付物/验收标准）→ 主公确认 → 执行 → 交付验收 → 归档。
- 提交 SHA 口径：同一内容因两侧独立推送导致 SHA 不同时，以远端为准，不重复补推，除非主公要求。

## 9. 可追溯与对账
- 提交记录=来源标签+类型，`git log --oneline` 可查。
- 每周日 AI交流 对账：双方汇报本周改动文件，Codex 抽查一致性；问题按第 3 条仲裁。

## 10. 与主公的接口
- 写操作完成 → 相关 AI 在主公当前对话一句话汇报（改了什么、为什么）。
- 需要告诉 WorkBuddy 的事项一律发到 D:\AI交流（「AI交流群」）。
- 危险操作批准：主公只回「同意/不同意」。
- 叫停：主公说「停」= 立即停止一切仓库写操作。
- 修订：任何一方提议 → AI交流 讨论 → 主公确认 → Codex 定稿 → 同步两份副本（D:\AI交流 + 仓库 docs/共管协议.md；仓库副本由 WorkBuddy 推送）。
